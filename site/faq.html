General

What exactly is Token Trail?

Token Trail is a free, open-source desktop dashboard for Linux that helps you understand your local OpenAI Codex usage. It presents six routes:

  • Overview: your primary quota window with used and remaining percentages, reset time, countdown, and last-updated freshness.
  • Quota Windows: every bucket Codex reports, grouped and sorted in deterministic attention order.
  • Usage: aggregate token activity over date ranges, with a daily chart, calendar heatmap, accessible table, and statistics.
  • Credits: balance, unlimited state, spending limits, and reset-credit expiry.
  • Learn: built-in explanations linked contextually from the metrics.
  • Settings & Diagnostics: themes, refresh choices, redacted diagnostics export, and clear-data.

It is strictly read-only: it observes account-level data reported by your own Codex CLI installation. It cannot start tasks, change your account, or redeem credits.

Is it really free? What is the license?

Yes. Token Trail is licensed under GPL-3.0-only, and the complete source code is public at github.com/amanalip/tokentrail. There is no paid tier, no account to create, and no subscription. Even the branding assets are original project artwork under the same license.

Which platforms are supported?

Linux desktop environments, for x64 (amd64) and arm64 (aarch64) machines. Four package formats ship: AppImage, deb (Debian, Ubuntu, Mint), rpm (Fedora, openSUSE), and Pacman (Arch, CachyOS, Manjaro).

Honest caveat from the support record: XWayland sessions have recorded evidence, while GNOME Wayland, Cinnamon, Xfce, and native X11 sessions are listed as untested so far. Untested does not mean unsupported; it means nobody has captured proof yet. arm64 artifacts build correctly but have not yet been executed on real hardware.

Compatibility and support matrix

What is the project's status?

The complete v1 read-only product scope is implemented and machine-verified across development versions 0.1.0 through 0.5.x. Each executable version carries its own screenshot-backed test report under tests/test_reports/<version>/, covering unit, integration, accessibility, end-to-end, security, packaged, and performance suites. On August 22, 2026, that entire automated matrix was re-executed green against a single commit — a rerun that caught and fixed one keyboard-focus defect on the Usage route. The project is moving through release validation: the tag-driven pipeline already assembles maintainer-reviewed drafts with structured notes, merged checksums, build provenance, and a CycloneDX SBOM, and the changelog plus support, maintenance, release-checklist, and incident-response policies are published. Artifacts remain unsigned development previews until an approved signing plan exists.

Changelog

Do I need a Codex account or subscription?

You need a working OpenAI Codex CLI installation, signed in to a Codex plan, resolvable from your normal PATH. Token Trail itself requires no account and no sign-in: it starts its own local Codex app-server process (codex app-server --stdio) and reads only what Codex reports for your existing authenticated session.

Who is Token Trail for?

For people who use Codex on their own Linux machine and want an honest picture of their capacity without opening a terminal or guessing from error messages: how much of each quota window remains, when windows reset, how much token activity happened across days, and what credits look like right now.

Is Token Trail affiliated with OpenAI?

No. It is an independent GPL-licensed project that talks to the locally installed Codex CLI through its documented app-server interface. All network activity belonging to your Codex usage stays inside Codex's own processes under its own terms; Token Trail adds nothing on top.

Does it show my OpenAI API usage or billing?

No, deliberately. Codex plan usage and OpenAI API billing are separate systems. Token Trail reads only local Codex app-server account data and never represents API billing state. Likewise, included plan usage flows through quota windows while credits are reported separately with their own units, and the two are displayed side by side without ever being added together.

Why do the files and commands say "tokentrail" without a space?

"Token Trail" (with a space) is the user-facing product name shown in the interface. "tokentrail" is the machine-safe identifier used where spaces and capitalization cause trouble: the repository, package name, executable slug, desktop entry, and protocol identifiers. The application keeps these roles strictly separated.

Privacy and security

Can Token Trail read my prompts or Codex conversations?

No, and this is an enforced boundary in code rather than a promise. Token Trail reads exactly three kinds of data (account information such as plan label, rate-limit snapshots, and aggregate usage buckets, plus credit information) through an allowlist checked before anything reaches Codex. Prompts, responses, tasks, repositories, files, tool calls, agent transcripts, and browser sessions are structurally outside what the application can request.

Responses are validated against closed schemas and stripped of every field outside the approved set before they cross into display logic; account email addresses are dropped intentionally at the schema level. The only other protocol traffic is the standard handshake required to start the app-server session and one rate-limit update notification that triggers a fresh approved read.

Privacy guide

Where is my usage data stored?

In RAM only, while the application runs. Usage snapshots, quota values, and session-to-session deltas live in memory; closing the window erases them completely. There is no history file, no cache, no crash dump containing them, and nothing for a future version to sync.

The only thing ever written to disk is your preferences document at ~/.config/Token Trail/preferences.json, containing display choices such as theme and refresh settings. Its schema structurally excludes usage values, timestamps, and account details, so they cannot appear in it even by accident.

What happens if my preferences file gets corrupted?

Preferences are validated on every load against a closed schema. A newer version reads older files fine, and invalid values are reset to defaults rather than breaking launch. A corrupt document is quarantined and reset safely but visibly, never trusted blindly. Clearing data from Settings & Diagnostics deletes the document after you confirm.

Does Token Trail have telemetry or make network connections?

No. No telemetry, no crash reporting, no analytics, no update checks, no remote fonts or assets. A repository-wide search finds no auto-update or update-check code anywhere, and the AppStream metadata tests actively forbid update-check language. The packaged build's Content Security Policy blocks remote script and style sources outright; the only URLs fetched are local file:// resources serving the app's own bundle.

Does Token Trail handle my login or API keys?

Never. Authentication belongs entirely to Codex. If you are signed out, Token Trail shows a signed-out state and you fix it by running codex login yourself. Credentials never pass through or rest inside Token Trail, so there is nothing stored to leak and nothing to re-enter inside the application.

Can it change my account or spend my credits?

No. Token Trail has no write access of any kind: no task control, no credit redemption, no account changes. The outbound allowlist contains only read methods, so a compromised or buggy component could not issue a write even if it tried.

How is the application hardened against attacks?

The Electron shell applies defense in depth: a sandboxed renderer with context isolation and no Node integration, a strict self-hosted Content Security Policy in production, deny-by-default handlers for navigation, redirects, popups, webviews, permission requests, and downloads, single-instance enforcement so a second launch focuses the running window instead, and Electron fuses that disable risky runtime behaviors. Renderer isolation is verified in development, built, and packaged modes on both display-server backends by automated tests.

Security boundaries guide

What is inside the diagnostics export? Is it safe to share?

The support document comes from a fixed, closed schema: application/Electron/Chromium/Node versions, platform and session details, theme, connection facts such as the last refresh category, and coarse sanitized health, coverage, and session counters. Email addresses, identifiers, file paths, prompts, responses, raw protocol messages, and unknown fields are structurally excluded.

This is backed by automated tests that plant canary values for every sensitive class and fail the build if any could leak. You always see a complete preview before choosing a save destination through the native dialog, so the exported file is designed to be safe to attach when asking for help.

What does "provenance" mean here?

Every value is labeled with its source: Codex-reported values come from the local app-server, calculated values are derived locally from those reported values, and locally observed values describe what this running process saw, such as when something was last refreshed. Provenance exists so honest numbers and honest gaps look different at a glance, and contextual links take you straight to an explanation whenever a metric surprises you.

Installation

Why are downloads called unsigned development previews?

Packages are not code-signed yet because no Linux signing identity has been approved for the project. That means your OS may show unknown-publisher warnings. Checksums are the verification mechanism until signing lands, so always verify before running anything:

sha256sum -c SHA256SUMS.txt --ignore-missing

Every downloaded file must print OK. A mismatch means the file is not the reviewed build; do not run it. Release pipelines also attach build provenance and a CycloneDX SBOM to each maintainer-reviewed draft release.

The AppImage will not start. What do I do?

Classic AppImages need FUSE 2 on most distributions:

sudo apt install libfuse2

On Fedora use sudo dnf install fuse; on the Arch family use sudo pacman -S --needed fuse2. As a fallback you can skip FUSE entirely by extracting and running in place:

./tokentrail-*-linux-x86_64.AppImage --appimage-extract-and-run

Note that the AppImage is the one format without embedded AppStream metadata today, an upstream tooling limitation recorded in the design decision log.

Troubleshooting guide

Are the "Source code" links on release pages installable?

No. The automatic zip and tar.gz snapshots contain repository text only, not a runnable build, and they are absent from SHA256SUMS.txt. Install only the tokentrail-* artifacts matching your architecture, named like tokentrail-0.5.0-linux-amd64.deb. Architecture suffixes map as: deb uses amd64/arm64, rpm and Pacman use x86_64/aarch64.

Where do the packages put their files?

Native packages install application files under /opt/Token Trail/, a launcher at /usr/share/applications/tokentrail.desktop, icons into the hicolor theme directories, and AppStream metadata at /usr/share/metainfo/com.tokentrail.app.metainfo.xml. The launcher declares StartupWMClass=tokentrail, so running windows associate correctly with the menu entry on Wayland and X11 alike. The AppImage is a single portable file with no other installed pieces; desktop-menu integration depends on your environment's AppImage handling.

Does it install services, autostart entries, or tray icons?

No. Token Trail installs no tray icon, no autostart entry, no background service, and no daemon. When the window closes, the process exits and everything in memory is gone. Nothing runs between sessions because there is nothing to run.

How do I check which version I have?

Open Settings & Diagnostics and expand the diagnostics preview: the application version appears alongside the Electron and Chromium versions it runs on. For package installs you can also ask your package manager directly:

dpkg -s tokentrail | grep Version # deb
rpm -q tokentrail # rpm
pacman -Qi tokentrail | grep Version # Pacman
How do upgrades work? Will it update itself?

v1 performs no update checks by design, so upgrading is always a manual act you decide on. Download the new artifact and its checksums, verify them, close Token Trail, then install over the old version with your package manager (or replace the AppImage file). Package managers replace application files in place; your preferences survive because they live in your user profile, not inside the package. Running copies refuse mid-flight replacement because of single-instance enforcement, which is why closing first matters.

Upgrading guide

Can I roll back to an older version?

Downgrading is not a supported path. Preferences written by a newer version may carry fields an older build does not understand; the older build quarantines and resets them safely but visibly, so expect settings to return to defaults. Published releases are immutable: files never change under the same name, and corrections ship as new versions.

How do I uninstall completely?

Delete the AppImage file, or remove the native package with your package manager: sudo apt remove tokentrail, sudo dnf remove tokentrail, sudo zypper remove tokentrail, or sudo pacman -R tokentrail. The packages declare no post-remove scripts, so exactly their own files are removed.

Your preferences intentionally survive in case you reinstall later. To erase those too, either clear data from Settings & Diagnostics first or delete the directory afterward:

rm -rf ~/.config/"Token Trail"

You can verify removal with which tokentrail: it should come up empty, along with the paths listed in the uninstalling guide.

Reading the numbers

What is a quota window?

A quota window is a rolling period, such as five hours or a week, for which Codex reports used and remaining percentages for its own capacity accounting. Because the window slides continuously rather than resetting at one fixed instant, the percentage can change unevenly over time even without unusual activity. Codex may report several buckets, such as primary and secondary, and Token Trail shows each one separately with its own duration, reset timestamp, and countdown.

What happens when I hit a limit?

A reached state appears on screen only when Codex reports it, and it applies to the specific bucket Codex named. Token Trail never predicts that you will be blocked and never assigns one bucket's reached state to another window. If a limit hits, the Quota Windows route surfaces reached-state reports first in its attention ordering so you see them without hunting.

My reset countdown passed but the number did not change. Is it broken?

No. Countdowns are calculated from the reported reset timestamp against your local clock, but when a reset time passes, Token Trail waits for a fresh snapshot from Codex rather than assuming the reset actually occurred. Refresh, or interact with Codex, and the next approved read updates the display with reality instead of an assumption.

What do the provenance labels on each value mean?

Every metric carries its origin with it:

  • Codex-reported: read directly from Codex.
  • Locally observed: measured locally by Token Trail, such as when a value was last refreshed.
  • Calculated by Token Trail: derived from reported source ranges.
  • Unavailable: not present, invalid, or unsupported by your Codex version, shown with a reason instead of an invented number.

Summaries over incomplete date ranges are additionally flagged as partial, with the covered dates shown, so a calculated total never quietly pretends to cover days it does not have.

Why does something show Unavailable instead of zero?

An empty-looking value can mean three different things, and Token Trail deliberately distinguishes them: reported zero (Codex said the value is zero), missing (Codex did not include the field), and unavailable with a reason (invalid, unsupported, or failed input). None of these is silently converted to zero. If your installed Codex version lacks support for an approved read, the affected metric shows unavailable while unrelated valid sections keep working; upgrading your Codex CLI usually restores the missing values.

Do token totals and quota percentages relate to each other?

They are related but not convertible, so Token Trail never converts one into the other. Token totals describe how much text went through Codex; quota percentages are reported separately by Codex for its own capacity windows. Blending them into a single number would invent meaning, which is why the interface refuses to do it.

How do statistics handle missing days?

A missing date stays missing and is never treated as zero. Strict comparisons require every date in both periods to be supplied, so a comparison against an incomplete range simply does not render rather than mislead. Coverage reporting explains exactly what was received for any range you select. The calendar heatmap makes the same distinction visually: positive days, genuinely reported zero days, and days where nothing was reported all look different.

Why is there no single health score combining everything?

Quota percentages, credit strings, spending controls, and reset-credit counts use different units reported through different mechanisms. Combining them into one score would invent meaning that no source stated, so Token Trail shows them side by side with their origins labeled instead. This is the same principle behind keeping token totals and quota percentages separate.

Will my history be there tomorrow?

No, by design. Changes since Token Trail opened compare the current snapshot against an in-memory baseline taken at startup; those observations disappear when the process exits and are never written to disk. v1 keeps no persistent history at all, which is the deliberate tradeoff behind its strongest privacy property: there is nothing stored to leak, subpoena, or sync.

When does the data refresh?

Data is read at startup, whenever you press the refresh control, and whenever Codex pushes a rate-limit update notification, which triggers a fresh approved read so quota changes appear without a click. Token Trail itself runs no polling timers. An automatic-refresh option exists in Settings but stays off by default and is not yet wired to any scheduler; the app labels this honestly as pending evidence.

What connection states can the Overview show?

Four, each stating reality plainly: connecting/loading while the owned Codex app-server starts, fresh data with per-value read times once values arrive, signed out when Codex reports no authenticated session, and unavailable when the Codex CLI cannot be found or answered incompatibly. Values appear only when Codex actually reports them, so gaps stay visible rather than masquerading as zeros.

Is the app usable with a keyboard or a screen reader?

Keyboard-only navigation works everywhere; press Tab after loading to reach the skip-to-content link, every route moves focus to its heading after you navigate — including Usage, whose chart loads lazily — and all routes maintain visible focus. Verified structural contracts back this up: one stable landmark inventory with a single heading per route, named regions for signed-out and error guidance, polite status semantics for connection updates, and an accessible name on every interactive control. Automated axe-core audits run against the built application alongside these semantic suites and keyboard-only end-to-end workflows in real Electron sessions. One honest gap from the support record: a full human-operated Orca screen-reader session has not yet been performed, since that requires operator judgment beyond automated checks.

Troubleshooting

Token Trail says the Codex CLI is unavailable, but codex works in my terminal.

This almost always means your desktop session's PATH differs from your shell's PATH, because menu launches do not read .bashrc. Confirm the CLI resolves in a terminal first:

which codex && codex --version

If that works but the application still cannot find it, link the directory containing codex into a standard location such as /usr/local/bin, then press refresh. Token Trail resolves the executable from the PATH environment it inherits, splitting it into absolute entries and checking each one.

It shows a signed-out state, but I am logged in.

Codex itself has no authenticated session visible to Token Trail. Fix it through Codex directly:

codex login

Then refresh. Token Trail never asks for credentials itself, so there is nothing to re-enter inside the application.

The menu entry, icon, or taskbar association is missing.

Native packages install a launcher at /usr/share/applications/tokentrail.desktop. If your menu lacks the entry, reinstalling the package restores it, or you can refresh your desktop database:

update-desktop-database ~/.local/share/applications 2>/dev/null || true

On X11 you can confirm what a running window reports with xprop WM_CLASS; it should contain tokentrail, matching the launcher's StartupWMClass on both Wayland and X11.

One metric is unavailable while everything else works. Should I worry?

No. If your installed Codex version does not support one of the approved reads, the affected metric shows as unavailable with a reason instead of failing the whole dashboard. Everything else keeps working, because one unsupported endpoint never erases unrelated valid sections. Upgrading your Codex CLI usually restores the missing values.

I launched a second copy and nothing appeared.

Token Trail enforces single-instance behavior: a second launch hands focus to the already-running window instead of starting another process. This is intentional, prevents split-brain readings, and is also why the upgrading guide tells you to close the app before replacing its files.

Where do I get help?

Export the redacted diagnostics document from Settings & Diagnostics (it previews everything before saving and is designed to be safe to share), then open an issue at github.com/amanalip/tokentrail/issues with the file attached. The troubleshooting guide covers most other cases, and the known-limitations page lists honestly what currently lacks evidence, such as unsigned artifacts and environments awaiting their first verified session.
